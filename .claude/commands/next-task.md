Выполни ровно одну задачу из `docs/PLAN.md` и остановись. Следуй правилам `CLAUDE.md`. Отвечай по-русски.

## 1. Выбор задачи и ветки
- Прочитай `docs/PLAN.md` и возьми первую задачу с `- [ ] Статус` (по порядку файла).
- Задача с пометкой `[Q-n]`, на которую нет ответа в разделе «Вопросы» или в `docs/DECISIONS.md`, — не начинай: задай вопрос и остановись.
- Номер этапа N берется из ID задачи (T-N.x). Текущая ветка должна быть `stage-N`:
  - `git status` чистый — иначе остановись и сообщи;
  - если ветки нет — создай её от актуального `main` (`git switch -c stage-N main`);
  - если есть — переключись на неё.

## 2. Анонс
Кратко покажи: ID и название задачи, что будет сделано, какие файлы изменятся. Если цель или критерии приемки неясны или противоречат SPEC — задай вопрос и остановись.

## 3. Реализация
- Реализуй задачу строго в рамках её цели и критериев приемки, вместе с тестами на новый код.
- Внешние API библиотек сверяй с актуальной документацией (Context7), не по памяти.
- Новая зависимость — с записью причины в `docs/DECISIONS.md`.
- Никаких действий на реальных серверах пользователя.

## 4. Мини-проверка (обязательны все пункты)
- `gofmt -l .` (пусто), `go vet ./...`, `go build ./...`
- `go test -race` затронутых пакетов
- `shellcheck` — если менялись скрипты
- Самопроверка `git diff`: соответствие каждому критерию приемки; нет мусора и отладочного кода; нет секретов; нет `TODO` без ссылки на задачу в PLAN.md.

Если что-то не проходит — исправь и повтори проверку целиком, не переходи дальше. После двух неудачных подходов к одной проблеме — остановись и опиши, что пробовал и что видишь.

## 5. Фиксация
- В `docs/PLAN.md` отметь задачу `- [x] Статус` и добавь под ней строку `- **Итог:** что сделано; что осталось за рамками`.
- Закоммить код, тесты и PLAN.md одним коммитом в Conventional Commits на английском, например `feat(config): add server registry (T-2.2)`. Без Claude-атрибуции.

## 6. Только для T-N.gate — полная проверка этапа
- `golangci-lint run`, `go test -race ./...` по всему проекту.
- Тесты скриптов в контейнерах `ubuntu:24.04` и `ubuntu:26.04`, включая повторный запуск (идемпотентность): `tests/scripts/run.sh 24.04 && tests/scripts/run.sh 26.04`. Если локально нет Docker — результат берется из CI-job `scripts`, и это явно указывается в отчете.
- Сверка каждой задачи этапа с её критериями приемки и требованиями F-xx; несоответствия — в отчет.
- Выведи ручной чек-лист этапа из PLAN.md для проверки на тестовом VPS.
- `git push -u origin stage-N`, открой PR в `main` (`gh pr create`), дождись завершения CI (`gh pr checks --watch`). Красный CI — исправить и повторить.
- Остановись и жди подтверждения пользователя перед слиянием и следующим этапом. Сам не сливай.

## 7. Отчет
- Что сделано (задача, ключевые файлы).
- Результаты проверок (команды и итог; что не проверено и почему).
- Следующая задача из PLAN.md.
