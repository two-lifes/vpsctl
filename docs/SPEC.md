# ТЗ: CLI-панель управления VPS и деплоем

Версия 0.1 (черновик) · Oct 26, 2026 · @Шарагулов Павел Андреевич

## 1. Цель

Консольное приложение (рабочее название `vpsctl`) заменяет ручную работу по SSH: показывает состояние VPS и проектов на них и разворачивает новый сервер или проект по одному стандарту.

Проблемы, которые решаются:

- Один и тот же деплой повторяется вручную на каждом сервере, шаги забываются.
- Нет общей картины: какие проекты запущены, какие упали, какие домены куда смотрят, сколько занято диска.
- Конфигурация серверов расходится, и новый VPS каждый раз настраивается заново.

Критерий успеха: новый VPS готов к деплою одной командой, новый проект разворачивается из репозитория за один сценарий без ручного SSH.

## 2. Термины и границы MVP

| Термин | Значение |
| --- | --- |
| Сервер | VPS, добавленный в `vpsctl`: адрес, порт, пользователь, SSH-ключ |
| Проект | Приложение из Git-репозитория, развернутое в `/opt/<проект>` |
| Манифест | Файл `vpsctl.yml` в репозитории проекта: как собрать, запустить, на каком домене |
| Bootstrap | Одноразовая подготовка нового VPS под стандарт `vpsctl` |
| Стандарт | Единая раскладка папок, пользователей, сервисов и nginx на всех серверах |

**Входит в MVP (v1):**

- Клиент только под Linux, управление по SSH.
- Список серверов, добавление сервера, bootstrap.
- Обзор сервера: ресурсы, сервисы, проекты в `/opt`, домены, SSL.
- Деплой, обновление, перезапуск, остановка, логи проекта.
- Обнаружение проектов, развернутых вручную до `vpsctl` (только чтение).

**Не входит в MVP:**

- Клиенты под macOS и Windows.
- Веб-интерфейс, мультипользовательский режим, роли.
- Мониторинг с историей и алертами (только текущее состояние).
- Kubernetes, кластеры, балансировка между серверами.

## 3. Пользовательские сценарии

**С1. Подключить новый VPS**

1. Запускаю `vpsctl`, выбираю «Добавить сервер».
2. Ввожу имя, IP, порт, пользователя и способ первого входа (root-пароль или уже загруженный ключ).
3. `vpsctl` проверяет отпечаток хоста и показывает его для подтверждения.
4. `vpsctl` выполняет bootstrap: создает пользователя `deploy`, кладет мой ключ, ставит базовые пакеты, отключает вход по паролю.
5. Сервер появляется в списке со статусом «готов».

**С2. Посмотреть, что происходит на сервере**

1. Выбираю сервер в списке.
2. Вижу сводку: CPU, RAM, диск, uptime, версия ОС, ожидающие обновления.
3. Вижу таблицу проектов: статус (работает / остановлен / упал), домен, SSL до какой даты, размер папки, последний коммит.
4. Отдельно вижу «неизвестные» папки в `/opt` и сервисы без манифеста.

**С3. Развернуть проект**

1. На сервере выбираю «Новый проект», ввожу URL репозитория и ветку.
2. Для приватного репозитория `vpsctl` создает на сервере deploy key и показывает публичную часть, чтобы добавить ее в GitHub.
3. `vpsctl` читает `vpsctl.yml` из репозитория; если его нет, предлагает создать по шаблону (`bot`, `web`, `web+db`, `static`).
4. Запрашивает значения для `.env` (секреты не сохраняются локально).
5. Через `vpsctl-deploy` клонирует репозиторий, тянет образ из GHCR (`docker compose pull` + `up -d`) или собирает на сервере, если образа нет; настраивает nginx и SSL для домена.
6. Предлагает workflow GitHub Actions для автодеплоя по push.
7. Показывает статус контейнеров и последние строки логов.

**С4. Обслуживание**

- Обновить проект (git pull + пересборка + перезапуск) с откатом на предыдущий коммит при ошибке запуска.
- Перезапустить, остановить, удалить проект с подтверждением.
- Смотреть логи в реальном времени.
- Открыть обычную SSH-сессию на сервер или в папку проекта одной клавишей.

## 5. Архитектура

В MVP на сервере нет постоянно работающего агента: клиент выполняет команды по SSH, а состояние собирает один скрипт-коллектор, который возвращает JSON.

&#91;embedded content: архитектура · клиент, VPS, GitHub\]

Коллектор копируется на сервер при bootstrap и обновляется клиентом при смене версии; парсить вывод `df`, `systemctl` и т. п. на стороне клиента не нужно.

- **Почему без агента:** нечего обновлять и защищать на каждом сервере, нет открытых портов кроме SSH.
- **Когда понадобится агент:** история метрик, алерты, автодеплой по webhook — это этап после MVP.
- **Реестр серверов** хранит имя, адрес, порт, пользователя и путь к ключу; при желании переиспользует `~/.ssh/config`.
- **Источник правды по проекту** — `vpsctl.yml` в репозитории; состояние на сервере всегда читается заново, локальный кэш только для быстрого старта.

## 6. Стандарт инфраструктуры на VPS

Каждый сервер после bootstrap выглядит одинаково; `vpsctl` опирается только на эту раскладку.

**Пользователи**

- `deploy` — владелец проектов, вход только по ключу, состоит в группе `docker`. Группа `docker` по правам равна root, поэтому доступ к `deploy` защищается так же, как к root.
- Вход под `root` по SSH отключается после bootstrap.

**Файловая система**

```
/opt/
  <проект>/
    app/            # git-клон: Dockerfile, compose.yml, vpsctl.yml
    .env            # секреты, права 600, подключается в compose через env_file
    data/           # тома контейнеров (БД, загрузки)
    releases.log    # история деплоев: дата, коммит, результат
/etc/vpsctl/
  server.yml        # версия стандарта, дата bootstrap
/usr/local/bin/
  vpsctl-deploy     # единый скрипт деплоя: его вызывают и TUI, и GitHub Actions
```

**Запуск проектов** — всё в Docker Compose, шаблон задается в манифесте:

| Шаблон | Что в compose | Доступ снаружи |
| --- | --- | --- |
| `bot` | Один контейнер приложения, без портов | Нет |
| `web` | Контейнер приложения, порт только на 127.0.0.1 | nginx → домен + SSL |
| `web+db` | Приложение + PostgreSQL, данные БД в томе `data/` | nginx → домен; БД только во внутренней сети compose |
| `static` | Сборка фронта в multi-stage Dockerfile, раздача nginx-контейнером на 127.0.0.1 | nginx → домен + SSL |

Автозапуск: systemd поднимает `dockerd` при загрузке, контейнеры стартуют по `restart: unless-stopped`. Отдельные systemd-юниты на проекты не создаются.

**Сеть и домены**

- nginx как reverse proxy; один файл на проект: `/etc/nginx/sites-available/vpsctl-<проект>.conf`.
- Сертификаты — certbot (Let's Encrypt), автообновление по таймеру.
- Файрвол ufw: открыты 22 (или кастомный SSH-порт), 80, 443.

**Манифест `vpsctl.yml` (черновик формата)**

```yaml
name: my-bot
template: bot            # bot | web | web+db | static
compose: compose.yml     # путь к compose-файлу в репозитории
image: ghcr.io/<user>/my-bot:latest   # null — собирать на сервере
env:                     # ключи, которые нужно спросить при деплое
  - BOT_TOKEN
  - DATABASE_URL
domain: null             # или app.example.com
port: null               # порт на 127.0.0.1, куда проксирует nginx
healthcheck: null        # например http://127.0.0.1:8080/health
```

Управляемое отличается от ручного по наличию `vpsctl.yml` в `/opt/<проект>/app/` и по префиксу `vpsctl-` в именах compose-проектов и конфигов nginx.

## 7. Bootstrap нового VPS

Bootstrap запускается один раз на сервер и приводит его к стандарту из раздела 6. Два способа входа:

| Способ | Как | Когда |
| --- | --- | --- |
| А. Из `vpsctl` | `vpsctl` входит под root по паролю или ключу от хостера и сам выполняет скрипт | Основной; пароль root используется один раз и не сохраняется |
| Б. Команда вручную | `vpsctl` генерирует одну строку с моим публичным ключом, я вставляю ее в веб-консоль хостера | Если SSH под root закрыт или нет пароля |

Шаги скрипта (идемпотентные, каждый проверяет, сделан ли он уже):

1. Проверить ОС: поддерживаются Ubuntu 24.04 LTS и 26.04 LTS; иначе остановиться с сообщением.
2. `apt update`, установить git, nginx, certbot, ufw, curl; Docker Engine и плагин compose — из официального репозитория Docker.
3. Создать пользователя `deploy`, положить публичный ключ, добавить в группу `docker`, выдать sudo только на `nginx -t`, reload nginx и certbot.
4. Настроить ufw: SSH-порт, 80, 443. Docker публикует порты в обход ufw, поэтому шаблоны открывают порты только на 127.0.0.1.
5. Отключить вход root и вход по паролю в `sshd_config`, проверить, что вход под `deploy` работает, только потом перезапустить sshd.
6. Создать `/opt` с владельцем `deploy`, `/etc/vpsctl/server.yml`, установить `/usr/local/bin/vpsctl-deploy`.
7. Включить unattended-upgrades для обновлений безопасности (по флагу).

Скрипт хранится в репозитории `vpsctl` и версионируется; в `server.yml` пишется его версия, чтобы позже доводить старые серверы до нового стандарта.

## 8. Интерфейс (TUI)

Полноэкранный терминальный интерфейс с навигацией с клавиатуры; ориентиры по удобству — k9s и lazydocker.

| Экран | Что показывает | Основные действия |
| --- | --- | --- |
| Серверы | Список: имя, IP, статус связи, число проектов, загрузка диска | `a` добавить, `Enter` открыть, `b` bootstrap, `d` удалить |
| Сервер | Сводка ресурсов + таблица проектов + блок «неуправляемое» | `n` новый проект, `s` SSH-сессия, `r` обновить данные |
| Проект | Статус, манифест, домен, SSL, коммит, история деплоев | `u` обновить, `R` перезапуск, `x` стоп, `l` логи, `e` `.env` |
| Логи | Поток логов проекта | `/` поиск, `f` пауза, `Esc` назад |
| Мастер деплоя | Пошаговая форма: репозиторий, ветка, `.env`, домен | `Enter` далее, `Esc` отмена |

Общие правила:

- `?` — подсказка по клавишам на любом экране, `:` — командная строка как в vim/k9s.
- Разрушительные действия (удаление, стоп) требуют ввода имени проекта.
- Долгие операции показывают вывод команд в реальном времени, а не только спиннер.
- Работает в терминале от 100×30 символов; цвета с fallback для 16-цветных терминалов.

## 9. Безопасность

- Пароли не хранятся нигде: root-пароль используется только на время bootstrap и держится в памяти.
- Доступ к серверам — только SSH-ключи; поддержка ssh-agent и существующего `~/.ssh/config`.
- Отпечаток хоста проверяется по `known_hosts`; смена отпечатка блокирует подключение до явного подтверждения.
- Секреты проектов живут только в `/opt/<проект>/.env` на сервере (права 600); локальный реестр хранит адреса и имена ключей, без секретов.
- Пользователь `deploy` получает sudo только на перечисленные команды, без shell под root.
- Доступ к приватным GitHub-репозиториям — deploy key на каждый проект (только чтение), а не личный токен.
- Все действия пишутся в локальный журнал (F-19).

## 10. Нефункциональные требования и стек

**Требования**

- Клиент: Linux x86\_64; установка одним файлом или одной командой.
- На сервере не нужен постоянно работающий агент: всё через SSH и стандартные утилиты.
- Сбор обзора сервера — один SSH-вызов скрипта-коллектора, который возвращает JSON; целевое время — до 3 с на сервер.
- Несколько серверов опрашиваются параллельно.
- Ошибка на одном сервере не ломает интерфейс для остальных.
- Конфиг клиента — читаемый YAML в `~/.config/vpsctl/`, его можно хранить в Git.

**Стек (решено)**

| Компонент | Выбор |
| --- | --- |
| Язык | Go |
| TUI | Bubble Tea + Bubbles + Lip Gloss |
| SSH | `golang.org/x/crypto/ssh` |
| Конфиг | YAML |
| Сборка и релизы | Статический бинарник linux/amd64, GoReleaser + GitHub Releases |

## 11. Этапы разработки

Каждый этап дает рабочий результат, которым можно пользоваться сразу.

1. **Стандарт и скрипты.** Стандарт (раздел 6), bootstrap, `vpsctl-deploy`, шаблоны compose для 4 типов, формат `vpsctl.yml`. Проверить вручную на тестовом VPS.
2. **Read-only обзор.** Реестр серверов, подключение, скрипт-коллектор, экраны «Серверы» и «Сервер», включая проекты, развернутые вручную.
3. **Bootstrap из клиента.** Добавление сервера и запуск bootstrap из TUI (способы А и Б).
4. **Деплой и управление.** Мастер деплоя, deploy keys, обновление, перезапуск, логи, nginx + SSL.
5. **Автодеплой.** Шаблон workflow GitHub Actions, вызывающий `vpsctl-deploy`.
6. **После MVP.** Режим команд без TUI, клиенты под другие ОС, бэкапы, мониторинг с историей.
