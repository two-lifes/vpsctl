# План выполнения vpsctl

Источник требований — docs/SPEC.md (F-xx), стандарт сервера — docs/SERVER-STANDARD.md, архитектура — docs/ARCHITECTURE.md. Задачи выполняются строго по порядку командой `/next-task`; одна задача — 1–3 часа, один коммит. Ветка этапа — `stage-N`; в конце этапа — PR в main.

Обозначения проверок:

- **mini** — `gofmt -l .` (пусто), `go vet ./...`, `go build ./...`, `go test -race` затронутых пакетов, `shellcheck` измененных скриптов.
- **scripts-docker** — `tests/scripts/run.sh` в `ubuntu:24.04` и `ubuntu:26.04`, включая повторный запуск.
- **full** — `golangci-lint run`, `go test -race ./...`, scripts-docker, CI зеленый.

Задачи с пометкой `[Q-n]` нельзя закрыть, пока на вопрос n нет ответа.

## Этап 1. Стандарт и скрипты (ветка `stage-1`)

Результат: bootstrap, `vpsctl-deploy` и шаблоны, проверенные в контейнерах и вручную на тестовом VPS.

### T-1.1 Тестовая инфраструктура скриптов
- [ ] Статус
- **Цель:** запуск тестов bash-скриптов в контейнерах Ubuntu 24.04/26.04 локально и в CI; общая библиотека функций.
- **Требования:** F-03, F-04 (основа), ADR-023
- **Файлы:** `scripts/lib/common.sh`, `tests/scripts/run.sh`, `tests/scripts/Dockerfile` (или аргументы образа), `tests/scripts/lib.sh`, `.github/workflows/ci.yml` (job scripts-docker)
- **Приемка:** `tests/scripts/run.sh 24.04` и `26.04` запускают пустой набор тестов и возвращают 0; падающий тест возвращает ≠0; `common.sh` дает `log`, `die`, `require_root`, `os_check`; job в CI запускается по matrix. `[Q-10]` — режим контейнера (privileged/systemd).
- **Проверки:** shellcheck, scripts-docker, unit-тесты `common.sh`

### T-1.2 Bootstrap: проверка ОС и установка пакетов (шаги 1–2)
- [ ] Статус
- **Цель:** скрипт останавливается на неподдерживаемой ОС и идемпотентно ставит базовые пакеты и Docker из официального репозитория.
- **Требования:** F-03, F-04
- **Файлы:** `scripts/bootstrap.sh`, `tests/scripts/bootstrap_packages_test.sh`
- **Приемка:** на подмененном `os-release` (Debian, Ubuntu 22.04) — код ≠0 до изменений; на 24.04/26.04 установлены git, nginx, certbot, ufw, curl, docker-ce, docker-compose-plugin; повторный запуск выводит `skip` для шага 2 и не меняет apt-источники.
- **Проверки:** mini (shellcheck), scripts-docker

### T-1.3 Bootstrap: пользователь deploy и sudoers (шаг 3)
- [ ] Статус
- **Цель:** создать `deploy` с ключом, группой `docker` и ограниченным sudo.
- **Требования:** F-03, F-04; SPEC §9
- **Файлы:** `scripts/bootstrap.sh`, `tests/scripts/bootstrap_user_test.sh`
- **Приемка:** права `~/.ssh` 700, `authorized_keys` 600; ключ не дублируется при повторе; `/etc/sudoers.d/vpsctl-deploy` 440 проходит `visudo -c`; `sudo -l -U deploy` показывает только разрешенные команды; `sudo -u deploy sudo -n bash` запрещен. `[Q-1]` `[Q-2]` — финальный список команд.
- **Проверки:** mini, scripts-docker

### T-1.4 Bootstrap: ufw и sshd (шаги 4–5)
- [ ] Статус
- **Цель:** настроить файрвол и отключить root/пароль только после подтвержденного входа под `deploy`.
- **Требования:** F-03, F-04; SPEC §7 п. 4–5
- **Файлы:** `scripts/bootstrap.sh`, `tests/scripts/bootstrap_net_test.sh`
- **Приемка:** правила ufw для SSH-порта, 80, 443; `sshd -T` → `permitrootlogin no`, `passwordauthentication no`; при неудачной проверке входа под `deploy` sshd не перезапускается и скрипт завершается ≠0; повтор — без изменений. `[Q-12]` — SSH-порт.
- **Проверки:** mini, scripts-docker (ufw/sshd — в объеме, допустимом контейнером `[Q-10]`)

### T-1.5 Bootstrap: раскладка, server.yml, unattended-upgrades (шаги 6–7)
- [ ] Статус
- **Цель:** создать `/opt`, `/etc/vpsctl/server.yml`, установить `vpsctl-deploy`, по флагу включить unattended-upgrades; финальный тест идемпотентности.
- **Требования:** F-03, F-04
- **Файлы:** `scripts/bootstrap.sh`, `tests/scripts/bootstrap_layout_test.sh`, `tests/scripts/bootstrap_idempotent_test.sh`
- **Приемка:** владельцы/права по SERVER-STANDARD §3; `server.yml` содержит версию скрипта; повторный полный запуск — код 0, все шаги `skip`, `bootstrapped_at` не меняется. `[Q-12]` — значение флага по умолчанию.
- **Проверки:** mini, scripts-docker (два запуска подряд)

### T-1.6 Спецификация `vpsctl.yml` и шаблоны bot, web
- [ ] Статус
- **Цель:** зафиксировать формат манифеста v1 и шаблоны compose/манифеста для `bot` и `web`.
- **Требования:** F-18, F-10
- **Файлы:** `templates/bot/{compose.yml,vpsctl.yml}`, `templates/web/{compose.yml,vpsctl.yml}`, `docs/SERVER-STANDARD.md` §8
- **Приемка:** `docker compose config` валиден; `restart: unless-stopped`; у `bot` нет `ports`; у `web` порт только `127.0.0.1`; `.env` через `env_file`.
- **Проверки:** `docker compose -f … config` в CI-контейнере, mini

### T-1.7 Шаблоны web+db и static
- [ ] Статус
- **Цель:** шаблоны для приложения с PostgreSQL и для статического фронта.
- **Требования:** F-18
- **Файлы:** `templates/web-db/{compose.yml,vpsctl.yml}`, `templates/static/{compose.yml,vpsctl.yml,Dockerfile,nginx.conf}`
- **Приемка:** у PostgreSQL нет `ports`, данные в `../data/`; `static` — multi-stage Dockerfile, nginx на `127.0.0.1`; `docker compose config` валиден. `[Q-11]` — пароль БД.
- **Проверки:** `docker compose config`, mini

### T-1.8 `vpsctl-deploy`: первый деплой и обновление
- [ ] Статус
- **Цель:** скрипт клонирует/обновляет репозиторий, проверяет `.env`, выполняет `pull`+`up -d` или сборку, пишет `releases.log`.
- **Требования:** F-10, F-11 (update), F-15 (клон по deploy key — использование ключа)
- **Файлы:** `scripts/vpsctl-deploy`, `tests/scripts/deploy_test.sh`
- **Приемка:** на локальном bare-репозитории с шаблоном `bot` — первый деплой создает `/opt/<p>/{app,data,.env,releases.log}`; при отсутствии ключа из `env` — ошибка до запуска; при `image: null` — `--build`; compose-проект называется `vpsctl-<p>`; повтор с тем же коммитом — успешен; строка в `releases.log` при успехе и ошибке. `[Q-4]` — парсинг YAML.
- **Проверки:** mini, scripts-docker (Docker в контейнере `[Q-10]`)

### T-1.gate Проверка этапа 1
- [ ] Статус
- **Цель:** подтвердить, что скрипты этапа соответствуют SERVER-STANDARD и готовы к ручной проверке на тестовом VPS.
- **Требования:** F-03, F-04, F-10, F-18
- **Проверки:** full; сверка T-1.1…T-1.8 с критериями приемки
- **Ручной чек-лист (тестовый VPS, только после подтверждения в чате):**
  - [ ] bootstrap на чистом Ubuntu 24.04 → код 0
  - [ ] повторный bootstrap → все шаги `skip`
  - [ ] `ssh root@…` отклонен, `ssh deploy@…` по ключу работает, по паролю — нет
  - [ ] `ufw status` — только SSH, 80, 443
  - [ ] `/etc/vpsctl/server.yml` корректен
  - [ ] деплой тестового `bot` через `vpsctl-deploy` → контейнер running, переживает `reboot`
  - [ ] `releases.log` содержит запись

## Этап 2. Read-only обзор (ветка `stage-2`)

Результат: TUI со списком серверов и обзором каждого, включая ручные проекты.

### T-2.1 Скелет Go-приложения
- [ ] Статус
- **Цель:** `cmd/vpsctl` с `--version` и пустой Bubble Tea-программой, выход по `q`/`Ctrl+C`.
- **Требования:** SPEC §10 (стек)
- **Файлы:** `cmd/vpsctl/main.go`, `internal/tui/app.go`, `go.mod`, `go.sum`
- **Приемка:** `go build ./cmd/vpsctl`; `vpsctl --version` печатает версию (ldflags); тест модели: `q` → `tea.Quit`.
- **Проверки:** mini, golangci-lint

### T-2.2 Реестр серверов (config)
- [ ] Статус
- **Цель:** загрузка/сохранение `servers.yml` и `config.yml` с валидацией и атомарной записью.
- **Требования:** F-01, SPEC §9 (без секретов), §10 (YAML в `~/.config/vpsctl/`)
- **Файлы:** `internal/config/`
- **Приемка:** учет `XDG_CONFIG_HOME`; файл создается с правами 600; дубли имен и пустой host — ошибка валидации; Add/Rename/Remove; при сбое записи исходный файл не поврежден; табличные тесты.
- **Проверки:** mini

### T-2.3 Переиспользование `~/.ssh/config`
- [ ] Статус
- **Цель:** разрешать параметры сервера (HostName, Port, User, IdentityFile) из `~/.ssh/config` по `ssh_config_host`.
- **Требования:** SPEC §5, §9
- **Файлы:** `internal/sshconfig/`
- **Приемка:** тесты на фикстурах: wildcard `Host *`, `Include`, отсутствующий файл не ошибка; явные поля реестра имеют приоритет. Новая зависимость — с обоснованием в DECISIONS.md.
- **Проверки:** mini

### T-2.4 SSH-клиент и проверка отпечатка
- [ ] Статус
- **Цель:** подключение по ключу/ssh-agent с проверкой `known_hosts`, выполнение команды со стримингом и таймаутами.
- **Требования:** F-02, SPEC §9
- **Файлы:** `internal/sshx/`
- **Приемка:** тест с in-process SSH-сервером: известный ключ — успех; неизвестный — ошибка `ErrUnknownHost` с отпечатком SHA256; измененный — `ErrHostKeyChanged`; таймаут подключения соблюдается; stdin/stdout/stderr и код выхода передаются.
- **Проверки:** mini

### T-2.5 Коллектор: хост и ресурсы
- [ ] Статус
- **Цель:** скрипт коллектора выдает секции `host` и `resources` JSON-схемы v1.
- **Требования:** F-05
- **Файлы:** `scripts/vpsctl-collect`, `tests/scripts/collect_test.sh`
- **Приемка:** вывод — валидный JSON (`jq -e`), соответствует ARCHITECTURE §4; сбой одной секции попадает в `errors[]`, код 0; нет зависимостей кроме стандартных утилит Ubuntu + установленных bootstrap. `[Q-7]`
- **Проверки:** shellcheck, scripts-docker

### T-2.6 Коллектор: проекты и неуправляемое
- [ ] Статус
- **Цель:** секции `projects` и `unmanaged`.
- **Требования:** F-06, F-09
- **Файлы:** `scripts/vpsctl-collect`, `tests/scripts/collect_projects_test.sh`
- **Приемка:** фикстуры в `/opt`: управляемый проект (с `vpsctl.yml`) и ручная папка; правильные `managed`, `size_bytes`, `git.branch/commit`; статусы `running/stopped/failed` по правилам ARCHITECTURE §4; контейнеры вне `vpsctl-*` — в `unmanaged.containers`.
- **Проверки:** shellcheck, scripts-docker

### T-2.7 Коллектор: домены, SSL, порты
- [ ] Статус
- **Цель:** секции `domains` и `ports`.
- **Требования:** F-07, F-08
- **Файлы:** `scripts/vpsctl-collect`, `tests/scripts/collect_domains_test.sh`
- **Приемка:** домены из `server_name` nginx-конфигов, привязка к проекту по `vpsctl-<p>.conf`; `ssl_not_after` из сертификата; порты с процессом/контейнером; время выполнения коллектора < 3 с на фикстуре. `[Q-5]`
- **Проверки:** shellcheck, scripts-docker

### T-2.8 Go: типы коллектора, доставка и запуск
- [ ] Статус
- **Цель:** встроить коллектор в бинарник, обновлять на сервере при смене версии, декодировать JSON.
- **Требования:** F-05…F-09, SPEC §5
- **Файлы:** `internal/collector/`, `scripts/vpsctl-collect` (embed)
- **Приемка:** golden-тесты декодирования JSON v1; неизвестная мажорная `schema_version` — ошибка; при несовпадении версии скрипт передается через stdin (тест с фейковым `sshx`-исполнителем). `[Q-7]`
- **Проверки:** mini

### T-2.9 Параллельный опрос серверов
- [ ] Статус
- **Цель:** опрос нескольких серверов параллельно с ограничением конкурентности и изоляцией ошибок; кэш для быстрого старта.
- **Требования:** SPEC §10 (параллельность, отказоустойчивость), ADR-008
- **Файлы:** `internal/poller/`
- **Приемка:** тест с фейками: ошибка/зависание одного сервера не задерживает остальные дольше таймаута; `parallelism` соблюдается; кэш пишется в `$XDG_CACHE_HOME/vpsctl/state/` и помечается как устаревший при показе; `-race` чисто.
- **Проверки:** mini (`-race`)

### T-2.10 Экран «Серверы»
- [ ] Статус
- **Цель:** список серверов: имя, IP, статус связи, число проектов, загрузка диска; `Enter` — открыть.
- **Требования:** SPEC §8, F-02 (статус связи)
- **Файлы:** `internal/tui/screens/servers/`, `internal/tui/`
- **Приемка:** тесты модели (сообщения → состояние → view-фрагменты); ошибка сервера видна только в его строке; рендер укладывается в 100×30.
- **Проверки:** mini

### T-2.11 Экран «Сервер»
- [ ] Статус
- **Цель:** сводка ресурсов, таблица проектов, блок «неуправляемое», домены/SSL, порты; `r` — обновить.
- **Требования:** F-05, F-06, F-07, F-08, F-09, SPEC §8
- **Файлы:** `internal/tui/screens/server/`
- **Приемка:** golden-тесты view на фикстуре JSON; неуправляемое отделено и без действий; `r` запускает повторный сбор; `Esc` — назад.
- **Проверки:** mini

### T-2.12 Общие элементы TUI
- [ ] Статус
- **Цель:** `?` — подсказка по клавишам на любом экране, `:` — командная строка, стили с fallback на 16 цветов.
- **Требования:** SPEC §8 «Общие правила»
- **Файлы:** `internal/tui/{keys,help,cmdline,styles}.go`
- **Приемка:** тесты: `?` открывает/закрывает help, содержимое из keymap текущего экрана; `:servers`, `:q` работают; при 16-цветном профиле Lip Gloss стили читаемы (тест профиля).
- **Проверки:** mini

### T-2.13 Переименование и удаление сервера
- [ ] Статус
- **Цель:** на экране «Серверы» переименовать сервер и удалить его из реестра (`d`) с подтверждением.
- **Требования:** F-01
- **Файлы:** `internal/tui/screens/servers/`, `internal/config/`
- **Приемка:** удаление требует подтверждения; реестр сохраняется; на сервере ничего не выполняется; тесты модели. Добавление — T-3.1.
- **Проверки:** mini

### T-2.14 Локальный журнал действий
- [ ] Статус
- **Цель:** запись всех действий клиента (что, где, когда, результат) в JSON Lines.
- **Требования:** F-20, SPEC §9
- **Файлы:** `internal/journal/`, места вызова в `internal/config`, `internal/poller`
- **Приемка:** путь `$XDG_STATE_HOME/vpsctl/journal.log`, права 600; конкурентная запись безопасна (`-race`); тест, что значения, помеченные как секрет, не попадают в журнал.
- **Проверки:** mini

### T-2.gate Проверка этапа 2
- [ ] Статус
- **Цель:** read-only обзор работает на реальных данных без изменений на серверах.
- **Требования:** F-01, F-02, F-05…F-09, F-20
- **Проверки:** full; сверка T-2.1…T-2.14 с приемкой
- **Ручной чек-лист (тестовый VPS после этапа 1, только после подтверждения в чате):**
  - [ ] сервер из реестра виден, статус связи «ok», обзор < 3 с
  - [ ] ресурсы совпадают с `free -b`, `df -B1`, `uptime`
  - [ ] тестовый проект — running, коммит и ветка верны
  - [ ] ручная папка в `/opt` и ручной контейнер — в «неуправляемом»
  - [ ] недоступный сервер в реестре не ломает экран
  - [ ] подмена ключа хоста в `known_hosts` блокирует подключение
  - [ ] терминал 100×30 и 16 цветов (`TERM=xterm`) — интерфейс читаем

## Этап 3. Bootstrap из клиента (ветка `stage-3`)

Результат: новый VPS добавляется и приводится к стандарту из TUI.

### T-3.1 Добавление сервера и подтверждение отпечатка
- [ ] Статус
- **Цель:** форма «Добавить сервер» (`a`): имя, IP, порт, пользователь, способ первого входа; показ отпечатка хоста для подтверждения.

- **Файлы:** `internal/tui/screens/servers/add.go`, `internal/sshx/`, `internal/config/`
- **Приемка:** валидация полей; отпечаток SHA256 показывается до записи в `known_hosts`; отказ — сервер не добавляется; тесты модели формы.
- **Проверки:** mini

### T-3.2 Вход под root по паролю (в памяти)
- [ ] Статус
- **Цель:** аутентификация паролем/keyboard-interactive для первого входа без сохранения пароля.

### T-3.3 Запуск bootstrap со стримингом вывода

### T-3.4 Проверка результата и статус «готов»

### T-3.6 Повторный bootstrap (`b`)
- [ ] Статус
- **Цель:** доводить существующий сервер до текущей версии стандарта.

### T-3.7 Смена отпечатка: блокировка и явное подтверждение

## Этап 4. Деплой и управление (ветка `stage-4`)

Результат: проект разворачивается из репозитория и обслуживается из TUI без ручного SSH.

### T-4.1 Пакет manifest
- [ ] Статус
- **Цель:** типы и валидация `vpsctl.yml` v1.
- **Требования:** F-10, F-16, F-18
- **Файлы:** `internal/manifest/`
- **Приемка:** табличные тесты: обязательные поля, enum `template`, `port` обязателен для web/web+db/static, правило имени, формат `domain`, URL `healthcheck`; сообщения об ошибках с номером строки.

### T-4.2 Встраивание шаблонов и создание манифеста
- [ ] Статус
- **Цель:** если в репозитории нет `vpsctl.yml`, предложить создать по шаблону.
- **Требования:** F-18, сценарий С3 п. 3
- **Файлы:** `internal/templates/`, `templates/`
- **Приемка:** рендер каждого из 4 шаблонов проходит `manifest.Validate`; результат совпадает с golden-файлами.
- **Проверки:** mini

### T-4.3 Deploy key для приватного репозитория
- [ ] Статус
- **Цель:** сгенерировать на сервере ключ на проект, показать публичную часть, использовать при клоне.
- **Требования:** F-15, SPEC §9
- **Файлы:** `internal/deploy/deploykey.go`, `scripts/vpsctl-deploy` (опция ключа)
- **Приемка:** ключ ed25519 в `~deploy/.ssh/vpsctl-<p>` (600), повтор не перезаписывает; клон использует `GIT_SSH_COMMAND` только с этим ключом; приватная часть не покидает сервер.
- **Проверки:** mini, shellcheck, scripts-docker

### T-4.4 Вход сервера в ghcr.io
- [ ] Статус
- **Цель:** `docker login ghcr.io` на сервере токеном `read:packages`, переданным через stdin.
- **Требования:** F-15
- **Файлы:** `internal/deploy/ghcr.go`
- **Приемка:** токен передается только через stdin (`--password-stdin`), не попадает в аргументы процесса, журнал и локальные файлы (тест на фейковом исполнителе).
- **Проверки:** mini

### T-4.5 Ввод и запись `.env`
- [ ] Статус
- **Цель:** запросить значения ключей из `env` и записать `/opt/<p>/.env` (600) без сохранения локально.
- **Требования:** F-14 (запись), сценарий С3 п. 4, SPEC §9
- **Файлы:** `internal/deploy/env.go`
- **Приемка:** экранирование значений (кавычки, `$`, переводы строк) — табличные тесты; права 600 и владелец `deploy`; значения не в журнале/кэше.
- **Проверки:** mini

### T-4.6 nginx: проект с доменом и без
- [ ] Статус
- **Цель:** генерировать `/etc/nginx/sites-available/vpsctl-<p>.conf`, проверять `nginx -t`, reload; без домена — доступ по IP:порт и правило ufw.
- **Требования:** F-16
- **Файлы:** `scripts/vpsctl-deploy`, `templates/nginx/`, `tests/scripts/deploy_nginx_test.sh`
- **Приемка:** при ошибке `nginx -t` конфиг откатывается, nginx не перезагружается; повтор идемпотентен; правило ufw только для проектов без домена. `[Q-2]` `[Q-3]`
- **Проверки:** shellcheck, scripts-docker

### T-4.7 Проверка A-записи и выпуск SSL
- [ ] Статус
- **Цель:** перед certbot убедиться, что A-запись домена указывает на IP сервера, затем выпустить сертификат.
- **Требования:** F-17, F-16
- **Файлы:** `scripts/vpsctl-deploy`, `internal/deploy/dns.go`, тесты
- **Приемка:** несовпадение IP → понятная ошибка, certbot не вызывается; совпадение → `certbot --nginx` для домена; повтор при валидном сертификате — skip. Тест резолвера на фейке.
- **Проверки:** mini, shellcheck, scripts-docker (certbot — заглушкой)

### T-4.8 Healthcheck и откат
- [ ] Статус
- **Цель:** после `up -d` дождаться старта/healthcheck; при неудаче вернуть предыдущий коммит и перезапустить.
- **Требования:** F-12, сценарий С4
- **Файлы:** `scripts/vpsctl-deploy`, `tests/scripts/deploy_rollback_test.sh`
- **Приемка:** заведомо падающий коммит → откат на предыдущий, код ≠0, `releases.log` с `rolled_back`; первый деплой без предыдущего коммита — только ошибка; таймаут healthcheck настраиваем.
- **Проверки:** shellcheck, scripts-docker

### T-4.9 Мастер деплоя
- [ ] Статус
- **Цель:** пошаговая форма (`n`): репозиторий, ветка, deploy key, манифест/шаблон, `.env`, домен → запуск `vpsctl-deploy` с потоковым выводом → статус и последние логи.
- **Требования:** F-10, F-15, F-16, сценарий С3 п. 1–5, 7
- **Файлы:** `internal/tui/screens/wizard/`, `internal/deploy/`
- **Приемка:** `Enter` далее, `Esc` отмена без изменений на сервере до финального шага; тесты переходов модели; ошибка шага показывается с выводом.
- **Проверки:** mini

### T-4.10 Экран «Проект»

### T-4.11 Обновление, перезапуск, стоп, удаление
- [ ] Статус
